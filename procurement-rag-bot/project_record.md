# 采购知识助手｜项目开发全流程记录
> 文件记录项目从构思、搭建、调试、踩坑、迭代全部过程，用于复盘学习。

## 1. 项目构思阶段
### 1.1 项目动机
本人有医药采购行业背景，想做一个和过往工作经验强相关的AI项目，区别于通用聊天机器人，体现行业+AI产品结合的优势。
采购工作中经常需要翻阅大量合同、协议文件、供应商资料，信息查找效率低，非常适合用RAG知识库做文档检索类智能体。
选择Coze扣子平台，不需要复杂后端开发，可以快速验证产品想法，专注智能体提示词、知识库设计，适合AI产品方向作品集项目。

### 1.2 需求梳理
用户角色：采购专员
用户痛点：
① 采购文档数量多，长文档阅读慢；
② 需要反复查找合同条款，容易遗漏细节；
③ 多人查阅文档，版本混乱；
目标：搭建智能体，上传采购文档，实现文档问答、摘要、信息提取。
非需求（能力边界，提前排除）：不生成正式合同、不提供法律咨询、不自动完成采购审批。

## 2. 搭建实施步骤
1. 在Coze扣子平台新建Bot，命名：采购知识助手
2. 利用obsidian工具创建知识库知识库，上传采购相关样本文档（采购规范、供应商资料等）
3. 配置知识库检索插件，设置召回片段数量，调整检索匹配策略
4. 编写系统提示词，完成角色设定、输出约束、幻觉禁止规则
5. 加入Few-shot少样本示例，给AI演示输入和期望输出格式，统一回答风格
6. 开启多轮对话记忆，设置上下文窗口限制，防止Token超限
7. 批量测试：设计多组测试用例，正常提问、边界提问、知识库不存在信息提问
8. 根据测试结果迭代提示词，修复幻觉、答非所问问题
9. 调试完成后发布智能体，生成公开分享链接

## 3. 测试用例与迭代记录
> 记录多次提示词版本修改、问题现象和优化方案
### 版本V1
问题：智能体经常编造文档不存在的条款，出现幻觉。
原因：没有强约束，大模型习惯自行补充信息。
优化：增加强制规则：如果知识库没有对应信息，直接回复：当前文档未收录该问题，请核对查询内容，禁止编造任何信息。

### 版本V2
问题：回答内容大段，文字杂乱，重点不突出。
原因：没有限制输出结构。
优化：增加输出格式约束，要求分点输出，关键信息加粗。

### 版本V3
问题：简单问题不能回答，容易遗漏信息。
原因：知识库召回片段分割不合适，多个文档信息无法全部放进上下文。
优化：调整知识库召回片段数量；同时在提示词要求优先列出查到的所有信息，标注来源文档。

## 4. 项目踩坑清单（面试加分，体现问题排查能力）
1. 检索结果不准确：文档分块过大，一块文本包含多个无关主题；分块过小，丢失上下文关联。
2. 上下文超限：多轮长对话，累积token超出模型上下文窗口，后续回答被截断。
    解决方案：设置对话记忆上限，清理过期历史对话。
3. Few-shot样例无效：样例写得太长、场景不匹配，模型无法模仿。
    解决方案：精简样例，样例和真实业务提问保持一致。
4. 图片无法在Github展示：图片文件名中文，上传后README图片加载失败。
    解决方案：统一全部截图命名为英文、下划线命名。

## 5. 学习复盘总结
1. RAG不是万能，知识库原始文档质量是决定回答质量的第一要素。文档杂乱、信息矛盾，AI输出结果就会出错；
2. 大模型产品不能只追求“能回答”，更重要是控制风险，做好边界约束，抑制幻觉，这是B端业务场景最核心的要求；
3. 提示词不是一次性写完就结束，需要「写提示词 → 设计用例测试 → 发现问题 → 修改提示词」循环迭代；
4. 搭建智能体的核心产品工作：定义用户、梳理场景、划定能力边界、设计异常兜底策略，代码只是实现手段；
5. 作品集项目价值：不仅是demo，重点体现自己思考过程、解决问题的思路，面试时可以完整讲清楚整个项目踩坑与优化。
