
# Project Record | 医药零售智能动销分析工作台开发记录

> 项目：AI工作流自动化 - 医药零售智能动销分析（Coze扣子）
> 开发时间：2026.10
> 开发平台：扣子 Coze 工作流 + UI Builder
> 定位：从0到1独立设计并落地，展示AI产品经理的架构思维与工程边界认知。

---

## 一、 需求定义

### 1.1 业务背景与痛点
在医药批发零售业务中，月度复盘的核心考核指标是**销售量**。
原有的业务链路中，需人工从多维度数据中提炼洞察，面临以下痛点：
1. **提炼难度大**：需重点关注哪些品种卖得好/差、相比去年如何变化、哪个供应商表现最好，人工提炼费时费力。
2. **计算易出错**：如果直接把原始明细给大模型算，它算不对同比、毛利，极易产生“算数幻觉”。
3. **数据需预处理**：现实中数据必须先在 Excel 中做透视表算好，大模型只适合做文本加工。
4. **报告撰写繁琐**：人工撰写报告耗时长，格式也不稳定。

### 1.2 核心业务需求
*   **输入**：用户需要提供已预计算好的多维度销售汇总表（Markdown格式）。
*   **输出**：AI生成具备业务洞察的动销分析报告，并能根据人工意见进行定向修改。
*   **人机协同**：必须支持人工审核环节，不通过时需回传意见重新生成。

### 1.3 非功能需求（关键约束）
1. **绝对禁止数据幻觉**：模型必须严格逐行读取，无数据必须如实标注，禁止推算未知数值。
2. **计算与生成分离**：严禁大模型进行加减乘除，指标必须在数据准备阶段完成。
3. **系统稳定性**：前端请求不能因后台AI审核节点而挂起，必须保证用户能正常操作。
4. **Token与成本控制**：单次流程消耗可预估，有防死循环机制。

## 二、 架构设计与技术选型

### 2.1 整体架构
采用 **“前端数据预处理（Excel） + 后端双工作流解耦 + UI Builder B端工作台”** 的混合架构。

### 2.2 扣子工作流核心节点配置
*   **开始节点**：仅接收 1 个变量 `sales_data` (String)，降低输入复杂度。
*   **工作流 A（生成初稿）**：接收 `sales_data`，经由大模型节点生成 `initial_report`，直接接入结束节点。
*   **工作流 B（修改报告）**：接收 `initial_report` 和 `modify_suggest`，大模型执行定向修改，输出 `final_report`。
*   **UI Builder 前端**：放弃聊天框，采用表单布局。包括【数据输入框】、【生成按钮】、【报告初稿Markdown】、【意见输入框】、【提交修改按钮】、【终稿Markdown】。

## 三、 版本迭代记录

### V1.0 单体循环工作流（技术验证阶段）
*   **方案**：单工作流，内置循环节点与人工审核问答节点。
*   **致命缺陷**：将带“问答节点”的工作流绑定到前端表单按钮后，前端直接请求超时挂起，系统卡死。
*   **结论**：聊天式的异步交互，无法匹配标准表单的同步请求。业务必须解耦。

### V2.0 双工作流解耦 + UI Builder（产品落地阶段）
*   **架构调整**：工作流解耦为 A_生成初稿 与 B_意见修改器。前端切换为 B 端表单 + Markdown 预览工作台。
*   **优化点**：
    1.  实现“数据录入 -> 生成初稿 -> 输入意见 -> 更新终稿”的标准化路径。
    2.  解决前端请求超时问题，系统稳定性极大提升。
    3.  加入成功/失败提示与等待文案，缓解用户对 LLM 耗时任务的焦虑感。

## 四、 核心提示词与配置细节

### 4.1 系统提示词 (工作流 A：初稿生成)

```text
你是一名资深的医药批发零售采购总监。你的任务是基于下方提供的销售汇总表，生成一份《月度药品销售动销分析报告》。

【执行规则】：
1. 结构自由：根据表格中实际存在的字段，自由发挥，生成最有洞察力的分析报告。
2. 强制生成：只要提供了数据，你必须立刻进行深度分析。绝不允许说“无数据”、“暂未提供”这类客套话，绝不允许拒绝生成。
3. 严禁篡改：绝不允许编造表格中不存在的数据。如果缺少某个指标（比如上月销量），请直接忽略它，只分析现有的数据。
4. 计算准则（极其重要）：绝不允许自行加减乘除！只能引用表格中已经计算好的“同比变化(%)”和“毛利额(万元)”。如果表格里没有现成的百分比，请直接写“缺少同比数据”，绝不要自己算。
5. 输出要求：用正式的商务汇报口吻，分点叙述，直接输出报告正文，不要有任何前言后语。

```

### 4.2 用户提示词 (工作流 B：意见修改)

```text
这是本月采集到的销售数据汇总表（包含供应商、品种、今年销售量、去年销售量、同比增幅等）：
{{sales_data}}

我的修改意见是：{{modify_suggest}}

请根据以上数据，输出一份专业的销售动销分析报告。
```

### 4.3 UI Builder 配置细节


*   **输入框/输出框**：高度设为 `固定 400px` 或 `适应内容`，避免塌缩。
*   **变量绑定**：前端按钮事件中，`Textarea1.value` 绑定 `sales_data`；`Markdown内容` 绑定工作流输出。
*   **状态提示**：在按钮下方添加静态提示“正在全力生成报告，预计需要 20~30 秒，请耐心等待...”，并配置成功/失败 Toast 提示。

## 五、 踩坑记录与问题复盘（面试核心素材）

### 坑1：大模型“算术幻觉”与Token超限
*   **现象**：直接给大模型原始明细，模型算错同比或上下文过长报错。
*   **解决**：采用“计算与生成分离”。前端输入必须先经 Excel 处理。提示词强约束：“只做文本加工，绝不加减乘除”。

### 坑2：大模型的“防御性反噬”
*   **现象**：提示词写了“缺字段提示用户补充”，导致模型发现没有“上月数据”时直接罢工，输出索要数据的客套话。
*   **解决**：加入“强制生成”铁律。告知大模型：“无论提供什么字段，必须先基于现有数据立刻生成报告，缺少的字段直接跳过，绝对不允许拒绝生成！”

### 坑3：前端请求超时（架构死局）
*   **现象**：V1.0 工作流带“人工审核节点”，前端按钮一点就卡死，无法响应。
*   **解决**：拆分为“初稿生成”与“意见修改”双工作流。前端按钮1调A，按钮2调B，彻底解决同步请求被异步节点挂起的问题。

### 坑4：UI Builder 的组件陷阱
*   **现象**：拖入“纵向列表”导致输入框联动；组件绝对定位导致重叠；Markdown 高度设为百分比变成一条线。
*   **解决**：用“容器”做流式布局，拒绝随意拖拽；高度必须用固定像素或“适应内容”；绑定变量下拉框找不到数据时，保存并 `F5` 刷新页面重试。

## 六、 后续可扩展优化的方向

1. **自动化数据接入（去 Excel 化）**：
   * 引入 Python 代码节点（Pandas），自动完成 Excel 透视表的 `group by` 和同比计算，实现从“人工预处理”到“全自动数据清洗”的跨越。
2. **多模态报告输出**：
   * 在报告生成后，追加一个“图表生成”插件或代码节点，自动将销售 TOP 10 数据渲染成柱状图，插入到报告最终输出中。
3. **企业级系统集成**：
   * 通过 Coze 的 API & SDK，将工作流接入公司内部的 ERP 或飞书审批系统，实现“数据变动 → 自动触发 → 审核推送”的全链路闭环。
4. **前端可视化升级**：
   * 利用 Coze 的 UI Builder，继续完善“桌面网页”应用，增加“数据历史记录”、“报告导出 PDF”等实用功能。
